## Confirmed diagnosis of the local-catalog failure

The installer's "Open local catalog..." action sends `check_catalog` with a
`local_file`, so the signed `.aklc` is verified and its rows are populated
locally. The subsequent download step never reads the adjacent `.aklp` files.

- `installer/package-pages.iss:261` — "Open local catalog..." button; `:265`
  selects a `*.aklc`; `:268` sends `check_catalog` with `local_file`.
- `src/installer_helper_windows.rs:233` — `Command::CheckCatalog` reads and
  verifies the local catalog through `PreparedCatalog::from_bytes`, so the
  13 rows populate successfully.
- `src/installer_helper_windows.rs:277` — `ConfirmDownload` runs
  `SelectedDownload::accept_and_download_with`, whose fetch callback is
  `package_download::download(pin, ...)` at `:304`.
- `src/package_catalog.rs:351` — `PinnedPackage::url()` is always
  `https://github.com/{repository}/releases/download/{tag}/{asset}`.
- `src/package_download/winhttp.rs:135` — the downloader accepts only
  `github.com`; `:200` returns `HttpStatus` for any non-200 response.
- `installer/package-pages.iss:118` — any `result=failed` maps to the generic
  "package operation failed" message.

Because the candidate tag `ui-candidates-20260912-r1` has no published assets,
the fetch fails. The local `.aklp` files are never consulted, so there is no
offline package import. A second possible contributor — opening the real
managed store from a legacy profile (`src/installer_helper_windows.rs:282`) —
must be ruled in or out from the saved helper reply/log before code changes.

## Scope and non-goals

Goal: deliver a supported offline local-package import, close installer and
lifecycle acceptance, then finish input adapters and physical/linguistic
acceptance without overstating readiness.

Non-goals: publishing assets/catalog, creating a GitHub release, regenerating
or exporting signing keys, migrating a user installation, and global input
automation.

## Invariants and constraints

- Fail-closed for profile, store and signature checks; never bypass them.
- Keep online download and local import distinct; no silent fallback between
  them.
- Never delete or overwrite user data (lexicons, exclusions, selections, legacy
  profile).
- Secrets only through a Project Memory staged handle; never in argv, logs,
  prompts, chat, source or repository files.
- VM snapshots and live state are not changed without explicit agreement;
  results are confirmed by durable receipts, not by timeout inference.
- Semantic navigation uses `lsp_mcpls` first; lexical search is an explicitly
  stated fallback.
- Non-interactive commands expected to exceed ~30 seconds use Longrun exactly
  once under `AGENTS.override.md`; with the active Goal, `wake_policy="goal"`
  and `automatic_wakeup=true`, then end the turn without polling.
- All content intended for GitHub is written in English.

## Stage 0 — Diagnose (read-only, before changes)

1. Read the saved helper reply/log from the last installer run: exact operation
   (`confirm_download` or other), `result`, and error code.
2. Separate the causes: (a) network 404 / unpublished tag, (b) opening the real
   managed store from a legacy profile, (c) other.
3. Check actual VM/profile state (whether the legacy profile was renamed is
   still unverified) without changing it.
4. Record the finding in Project Memory as an occurrence/checkpoint.

Exit: one unambiguous cause plus a Project Memory entry. Code changes start only
after this.

## Stage 1 — Supported offline local-package import (primary)

1. Attach a local artifact source to the local catalog session:
   - carry the `local_file` directory from `Command::CheckCatalog` into
     `PreparedCatalog`/`SelectedDownload`;
   - resolve each artifact from the local directory by its `asset` name; in a
     local session the network path is forbidden.
2. Keep every existing check: `PinnedPackage::verify_download` and
   `check_package` (SHA-256, length, Ed25519, id/revision/locale/input) plus the
   revision high-water marks in `package_inventory`.
3. Path safety: absolute path; reject `..`, `.`, reparse points, symlinks and
   non-`.aklp`; bound by `MAX_PACKAGE_BYTES`; read with no-follow semantics.
4. UI: local and network paths are already separate buttons; make the text
   explicit that the local mode does not require network.
5. Documentation: update `docs/online-package-manager.md`,
   `docs/installer-package-selection.md` and `docs/package-release-catalog.md`.
6. Errors: replace the generic message with safe operation/cause context and no
   paths or secrets.
7. Tests (portable fixtures plus native): successful signed `.aklp` import;
   tampered hash/length/signature; wrong id/revision/locale; missing, oversized,
   traversal and symlinked files; no network request in a local session; a
   helper-level `check_catalog(local) -> select -> confirm_download ->
   confirm_install` scenario.
8. Verification: `cargo test`, strict Clippy, Windows build; refresh receipts
   and the rehearsal.

Exit: a local catalog with adjacent signed `.aklp` files installs offline
without publication, and the online path does not regress.

## Stage 2 — candidate2 fence / install / uninstall / cross-session

1. Validate PowerShell syntax (`tools/vm_installer_fence.ps1`,
   `tools/run_vm_installer_fence.py`) and the baseline before a single run.
2. Submit once through Longrun with the enrolled encrypted test asset
   (stdin secret); receipt directory `target/vm-installer-fence-20260913-01`.
3. Scenario: a held shared reader refuses setup (helper code 12); release the
   reader, install candidate2, uninstall, and verify the profile/CURRENT/sentinel
   are preserved and the fence is released.
4. Real cross-session runtime exclusion (simultaneous different sessions) is a
   separate check.
5. Do not replay setup on uncertainty; recover from per-operation
   process/exit/result receipts over SFTP.

Exit: fence and data preservation confirmed by receipts; uncertain operations
are never replayed.

## Stage 3 — Installer selection lifecycle acceptance

Verify zero, one and multiple selections; explicit license review and install;
cancellation at each phase; download failure; retry; helper/parent exit and
recovery; page transitions. Confirm unselected assets are never requested.
Record receipts and screenshots of owned windows only.

## Stage 4 — Upgrade and interruption (agreed VM)

Test a real upgrade from an older installed binary (not same-version repair),
interruption behavior, and the recoverable path. Decide explicitly about reboot
or snapshot rollback; do not treat them as a side effect of a diagnostic step.

## Stage 5 — Input packs, adapters and physical acceptance

Complete missing packs, scoring calibration and composition/IME, dead-key,
AltGr and grapheme adapters. Physically test typing, focus, undo, clipboard
preservation and protected-input boundaries in Notepad, Terminal and a browser,
keeping readiness conservative. UI language stays independent of input
readiness.

## Stage 6 — Acceptance completion and release gate

Finish the full 14-language UI, RTL, fonts, accessibility and linguistic review.
Confirm OS/filesystem requirements, complete dependency/dictionary notices, and
signing/recovery. Publish versioned packages/catalog and a signed installer only
as a separate, explicitly reviewed release action.

## Order and dependencies

Stage 0 -> Stage 1 (local, no VM) -> Stages 2/3 (VM, after a successful
installer build) -> Stage 4 -> Stage 5 -> Stage 6. Stages 2 and 3 are partly
parallel. Publication is blocked until the Stage 5–6 gates pass.

## Definition of done

- Stage 1: offline local import passes portable and native tests; no network in
  a local session; no online regression; documentation updated.
- Stage 2: fence and data preservation confirmed by receipts; cross-session
  exclusion confirmed.
- Stage 3: all selection/cancellation/recovery scenarios confirmed.
- Stage 4: upgrade and interruption verified in the VM; the difference from
  same-version repair is recorded.
- Stages 5–6: physical typing, languages, accessibility and notices closed;
  only then is a release discussed.

## Risks and reporting

- The exact log cause is unknown until Stage 0.
- The VM legacy profile may not have been renamed, so setup may still refuse.
- The catalog expires 2026-09-19; recheck and increment revisions on reuse.
- Windows stdout encoding has hidden successful operations before; rely on
  receipts.
- Per-operation receipts live under `target/`; Project Memory records the
  failure cause, the local-artifact resolution decision, and stage checkpoints;
  `handoff.md` is updated when state changes.

Do not mark the Goal complete until these acceptance gates pass. Do not publish
a release within this Goal.
